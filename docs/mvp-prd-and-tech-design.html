01MVP 的目标与判据

MVP 只回答一个问题：用户收到一条主动推送的引荐之后，会不会去看、会不会表态。会，这个产品就成立，后面的 AI、邮件、深度档案才有意义。不会，那问题出在引荐本身，加多少功能都救不回来。

这句话决定了取舍的方向。凡是不能提高「有人收到引荐 → 有人回应」这条链路的，MVP 里都不做。

1.1唯一的成功判据

主判据
引荐回应率 ≥ 40%
递出后 7 天内，至少一方表达「想认识」或「不合适」的比例。这个数是产品有没有价值的唯一硬证据。
护栏
「不合适」占比 ≤ 60%
回应率高但全是「不合适」，说明匹配引擎在乱推。回应率必须和拒绝率一起看。
护栏
推送打开率 ≥ 25%
打开率塌了，回应率再高也没意义 —— 那只说明推送本身没送达或没吸引力。

三个数都按 V1 真实数据回归校准，当前取值是判断用的起点，不是承诺（沿用完整版 PRD 第 10 条决策）。

1.2MVP 不在什么时候算完成

MVP 的结束条件是「拿到上面三个数」，不是「功能上线」。跑够样本量之前不加功能。这个约束要写进排期，否则 MVP 会一路长成完整版。

04功能需求

4.1注册登录

  • 邮箱 + 密码，注册与登录是两个入口，不再合并
  • 密码用 bcrypt，代价因子 12（约 200–300ms）。只限最短 8 位，不强制字符类别 —— 复杂度规则会把用户逼向 Passw0rd! 这种更难记又没更强的密码
  • 邮箱按 lower(email) 唯一。用函数索引而不是 CITEXT 扩展，也不依赖 service 层每次都记得转小写 —— 漏一次就是两个账号
  • 新用户建 users 行 + 一条空的 profiles 行，status = onboarding；建档向导只做 UPDATE，不做 INSERT
  • 连续 5 次密码错误锁 30 分钟（ACCOUNT_LOCKED）。计数在 Redis，按邮箱与 IP 两个维度分别计：只按邮箱计，攻击者可以遍历邮箱把全站账号锁死
  • 登录响应返回 next_step（onboarding / home），前端据此决定落地页
这一版砍掉了什么

没有验证码，没有找回密码，没有邮箱验证 —— 这三件事都需要一条外发通道，而 MVP 只有 Web Push。两个后果要认：

  • 邮箱永远是未验证的标识符。批量注册一个邮箱比批量注册一个手机号便宜得多。完整版 PRD 10.1 把手机号列为必须项，理由是「引荐是直接推给别人的，假档案的代价比滑动产品高」—— 手机号那条删除，不是放宽，但要看清接手的另外三条什么时候才到：真实人像检测（头像必过正脸检测）M1 就有，照片先审后发与入池前文本先审要等 M5 的审核队列。M1–M4 之间照片和文本都是上传即生效的，这一段唯一的自动门槛就是人脸检测。代价是有上限的，别假装没有
  • 忘记密码只能由运营重置。M1 就要提供 POST /api/v1/admin/users/:id/password（ADMIN_TOKEN 鉴权），README 里附一条 curl。真正的自助找回等 V1.1 有邮件通道之后

注册接口返回 EMAIL_TAKEN（409）是绕不开的泄露：不告诉用户邮箱被占了，他就不知道该怎么办。登录接口不泄露（邮箱不存在与密码错误返回同一句 INVALID_CREDENTIALS）。压住枚举速度靠 IP 限流，见第 21 节。

4.2建档与完整度

两段式，这是完整版 PRD 5.2 的简化落地。

入池门槛（第一段，必填 8 项）

字段取值为什么是必填
nickname2–12 字，过滤联系方式引荐卡上要有称呼
genderM / F，设定后不可改决定异性匹配，改它等于换一个账号
birth_ymYYYYMM，18–60 岁年龄是硬条件的基础
city_code国标 6 位，110000–829999地域是硬条件的基础
height_cm140–210软偏好可筛，不填等于放弃一项匹配信号
weight_kg35–150与身高成组。只问一半，外形这一组在池子里就是半张档案（v1.6 加）
education_level大专及以下 / 本科 / 硕士 / 博士同上
school_name≤40 字，自由文本；层级由 schools.TierOf 归一与学历成组。自由文本是必须的 —— 校不在库里也得填得进去，否则「必填」会变成「填不出来」（v1.6 加）
avatar_key一张通过审核的头像没有脸的引荐卡没人会点

照片另算：≥1 张才入池。头像单独判，它不在 profiles 的标量字段里，沿用 stubborn-love 的做法。

门槛从 3 张降到 1 张（v1.4）：首次建档要在两分钟内走完，把「传够 3 张」摆在门口会把人挡在门外。照片信息量不足会压低响应率这个理由没有消失，但它现在是建议而不是门槛 —— 前端照 3 张的软目标催（PHOTO_GOAL），后端只认 1。引荐卡的封面取 position = 0 那一张，所以 1 张的卡是完整的卡，不是残缺的卡。

照片数不进 completeness（与 birth_day 同理），所以这次改动不碰候选集的 completeness >= 60 门槛，也不需要迁移。另有一条保护：最后一张照片不给删（LAST_PHOTO）—— 删照片不会把 status 退回 onboarding（那是有意的，已建立的引荐不该失效），所以「在池子里却没有封面」这个状态必须事前拦住。换照片的路径是「先传新的，再删旧的」。

birth_day（出生日 1–31）不在门槛里，也不进完成度。它是界面上「出生日期」三级联动的第三级（年 → 月 → 日），只把生日显示完整。年龄始终按 birth_ym 的月粒度算，日不参与任何计算：加进门槛会让存量老用户（只知道年月）的完成度掉到门槛以下，静默掉出候选池。

深度档案门槛（第二段，选填 10 项）

选填项按模块分组渐进填写，不强制一次填完。填到 完成度 ≥ 60% 才进「可被别人看到」的名单。

模块选填字段组内项数
基本盘补充hometown_code · occupation · company · income_band4
生活方式chronotype · smoking · drinking · hobbies4
自述intro · expectation2

完成度算法沿用 stubborn-love 的 60/40 结构，但必填基数从 11 项改为 9 项（含头像），选填从 6 项改为 10 项：

// completeness 算 0..100 的资料完整度。不参与匹配打分，只做门槛。
// 必填占 60 分，选填占 40 分 —— 选填给足权重，是为了让用户有动力补。
func completeness(p *model.Profile, photoCount int) int {
    const totalRequired = 9   // 8 标量 + 头像
    filledRequired := totalRequired - len(missingRequired(p))

    optional := []bool{
        p.HometownCode != nil,
        p.Occupation != "", p.Company != "", p.IncomeBand != nil,
        p.Chronotype != nil, p.Smoking != nil, p.Drinking != nil,
        p.Hobbies != "", p.Intro != "", p.Expectation != "",
    }
    filledOptional := 0
    for _, ok := range optional {
        if ok { filledOptional++ }
    }

    score := float64(filledRequired)/float64(totalRequired)*60 +
        float64(filledOptional)/float64(len(optional))*40
    return int(score + 0.5)
}
不对称

能收引荐，和能被引荐，是两个门槛

只过入池门槛的用户能收到引荐，但不会被引荐给别人（决策 16）。这是驱动补全的杠杆：他想被看见，就得把深度档案补到 60%。

页面上的呈现（v1.6 改）：不报完成度、也不列「还差哪几项」。首页空状态只说「暂时没有新的引荐。我们在替你看着。」；「我的」页只说进没进池子 —— 进了就是「入池条件已满足，可以收到引荐了」。分数留在服务端，它是门槛不是进度条；缺项该在编辑页里对着字段看，而不是在首页挂一张用户此刻够不着的清单。

分步保存与续填

每一步提交一次 PUT /me/profile 局部更新，服务端 merge。这一条沿用 stubborn-love。

但它的续填是断的，MVP 必须补上。stubborn-love 的前端表单 ref 从不回填，中途刷新会从第 1 步重来，已提交的数据还在服务端但界面上看不见。MVP 的做法：进入建档页时先 GET /me/profile，把已填字段回填进表单，并跳到第一个未完成的步骤。

4.3偏好设置

双层结构照完整版 PRD 6.1，MVP 每层各取一部分。

层MVP 字段行为默认
硬条件 birth_ym 区间 · city_codes · 婚育意愿 · 是否接受有婚史 · 异地接受度 一票否决，不满足绝不互推 仅年龄必填，其余「不限」

「不限」三处协同（存储为空 → 打分时该维度不计入分母 → 界面上显示为「不限」而非空），沿用 stubborn-love。这一条看着小，做错会让用户以为自己的偏好被无视了。

4.4引荐的产生与生命周期

机制细节在第 12、13 节，这里只说用户看得见的部分。

  • 成对优先。双方双向分数都过线，才同时递出、同时通知（决策 13）
  • 池子不足时降级为单向。对方分数过线即可递出，对方不收到通知；若对方之后看到你并表达兴趣，才成匹配。阶梯照完整版 PRD 2.4
  • 一次推送携带 1–3 个人。列表再长就又变成刷了
  • 时限：未查看 72 小时、已查看未表态 7 天、已表态等对方 7 天。超时释放
  • 不设推送次数上限，也不设保底（决策 14）。这一周够格的组合有几个就推几个，可能整月为零

4.5触达：Web Push

  • 通道：浏览器推送，VAPID 签名。MVP 不做邮件兜底
  • 授权时机：在建档完成之后、第一次引荐可能到来之前请求，不在进站第一屏就弹（完整版 PRD 8.1）
  • 用户拒绝授权时，保留未读角标与站内提示条，下次访问且存在待查看引荐时再问一次，不重复弹窗
  • 静默时段：22:00–09:00 不推送，除非用户自行调整
  • 未响应冻结：连续 2 次推送都未打开，暂停推送转为站内提示，直到用户主动访问一次

4.6表态与匹配

  • 引荐页展示：照片、昵称、年龄 · 城市 · 学历 · 职业、年收入区间、身高，以及时间余量
  • 两个动作：想认识（零摩擦，一次点击）与不合适（原因三选一必填：条件不符 / 感觉不合适 / 其他，不需要输入文字）
  • 双方都「想认识」→ 立即成立匹配，建会话，向双方推匹配通知
  • 任一方「不合适」→ 本次终结，等待方立即收到中性收尾通知

4.7站内会话

  • 匹配成立后开启，纯文字，1–1000 字
  • 实时收发，复用 stubborn-love 的 WebSocket hub + Redis Pub/Sub
  • MVP 不做图片、语音、撤回、已读回执以外的任何能力
  • 消息中的联系方式记录但不拦截（沿用 stubborn-love 的取舍：匹配后交换微信是主流行为，硬拦伤体验）
  • 拉黑后会话立即关闭，双方都不能再发

4.8收尾通知

决策 17 的落地。这张表是实现依据，不能只按「发个通知」理解。

终结方式谁收到文案时机
超时释放 expired 超时未回应的一方 「你错过了 1 位合适的人」。只报这一次，不做累计，不写「你已错过 N 位」 到期即刻
超时释放 expired 已表态「想认识」的一方 「上封信没有等到回音。这位已经回到池子里了，遇到合适的再给你写信」 到期即刻
被明确拒绝 declined 已表态「想认识」的一方 与上一行完全相同的措辞，不区分原因 立即

  • 单向引荐不产生错过提醒，对方从头到尾没收到过东西
  • 这两类通知不受未响应冻结限制 —— 它们是一条引荐的收尾，不是新的招揽，恰恰是发给不常来的人的
  • 每条引荐各只发一次，绝不叠加

4.9安全与后台

  • 敏感词过滤：昵称、兴趣、自我介绍、期待、职业、单位、会话消息。种子词表必须替换为合规完整词表，否则等于没过滤
  • 文本签名比对：已 active 的用户改到文本字段才标记待审核；只改枚举/数值（身高、收入带等）不触发。被拒时从快照恢复，用户保持可用
  • 举报：fake / harassment / porn / ad_fraud / other；被 3 个不同用户举报自动转 under_review
  • 拉黑：双向不可见、不可被引荐、会话关闭
  • 注销：标记 deactivated，档案与照片 30 天内彻底删除，历史引荐匿名化
  • 后台：三合一审核队列（头像 / 照片 / 资料）+ 用户查询 + 封禁（封禁同时递增 token_version 让 token 立即失效）

7.2刻意不做的事

不做理由
消息队列（Kafka / RabbitMQ）投递量级是每天几百条推送。outbox 表 + FOR UPDATE SKIP LOCKED 足够，且已经在 stubborn-love 里验证过
分布式锁（redsync / etcd）只有「引荐生成任务不重复跑」一处需要互斥，用条件 UPDATE 抢租约即可。为此引一个锁库不划算
gRPC / 微服务拆分单体 + 两个进程。拆开只会让「引荐生成」这种跨表事务变难
Elasticsearch候选集是「异性 + 同城 + 硬条件」，走 PostgreSQL 复合索引就够。全文检索 MVP 不需要
Kubernetes单机 compose。MVP 的可用性要求是「挂了能起来」，不是「不挂」
配额机制决策 14 是不设上限也不设保底，所以 stubborn-love 的 quota Lua 脚本、quota:like 键、DB 兜底查询整套都不搬

刻意不做高可用

  • Redis 开 AOF everysec，崩溃最多丢 1 秒计数。MVP 的 Redis 里没有不可重建的数据
  • MinIO 单盘。照片是用户上传的不可再生数据，这是唯一需要外部备份的东西，用 cron 做 mc mirror 到异地
  • 数据库每日 pg_dump 到对象存储，保留 14 天
唯一的真风险

照片和数据库是仅有的不可重建资产

其他所有东西（Redis 计数、outbox 队列、hash 缓存）都能从 PostgreSQL 重建。备份只做这两样，但要真做。MVP 阶段最常见的翻车不是并发写坏，是服务器重装时才发现没有备份。

两个 compose 文件，不用 override

沿用 stubborn-love 的做法：docker-compose.yml（开发）与 docker-compose.prod.yml（生产）互相独立，后者不是前者的 override。原因是 compose 合并 ports 列表时是追加而不是替换，用 override 无法把开发环境暴露的数据库端口去掉。

分层纪律（照抄，这是它最有价值的部分）

  • SQL 一律走 db.Raw 配 ? 占位符，严禁 fmt.Sprintf 拼接（repo/repo.go 的包注释明确写了这条）
  • 所有事务边界走 Repo.Tx(fn func(tx *gorm.DB) error)；需要入队 outbox 的写操作，EnqueueNotify(tx, ...) 接收外层 tx，让通知写进同一个事务

  • 列表结果用 make([]T, 0)，否则 JSON 是 null，前端 .length 会白屏

CREATE TABLE introductions (

    batch_id      UUID        NOT NULL,   -- 同一次推送携带的 1–3 条共享

    user_low      BIGINT      NOT NULL REFERENCES users (id),
    user_high     BIGINT      NOT NULL REFERENCES users (id),

    state         TEXT        NOT NULL DEFAULT 'pending',

    hidden_side   TEXT,                 -- NULL | 'low' | 'high'

    high_viewed_at TIMESTAMPTZ,

    high_action_at TIMESTAMPTZ,

    score_high_to_low REAL,

    expires_at    TIMESTAMPTZ NOT NULL,
    closed_at     TIMESTAMPTZ,

    CONSTRAINT intro_state_chk CHECK (state IN ('pending','viewed','responded','matched','declined','expired')),
    CONSTRAINT intro_order_chk CHECK (user_low < user_high),

        (low_action IS NULL OR low_action IN ('like','pass')) AND
        (high_action IS NULL OR high_action IN ('like','pass'))

);

CREATE TABLE outbox (
    id            BIGSERIAL PRIMARY KEY,
    channel       TEXT NOT NULL,          -- push | email（email 留到 V1.1）
    user_id       BIGINT NOT NULL REFERENCES users (id) ON DELETE CASCADE,
    template      TEXT NOT NULL,          -- intro_delivered | intro_missed | intro_closed | matched
    payload       JSONB NOT NULL DEFAULT '{}'::jsonb,

12匹配引擎

MVP 是规则引擎，不是 AI。它要足够简单到能被人读懂和手调，因为 MVP 期间唯一的优化对象就是它。

12.1三步走

  1. 01候选集召回。用一条 SQL 取出「可能合适的人」——异性、同城或同省、年龄在硬条件区间内、已 active、未被拉黑、没有未终结的引荐。
  2. 02硬条件过滤。逐条判婚育意愿、婚史接受度、异地接受度。任一不合直接淘汰，不打分。
  3. 03双向打分 + 阈值判定。算 A→B 与 B→A 两个分数。两个都过阈值 → paired；只有一个过 → 按池子阶梯决定是否发 oneway。

12.2打分公式

六个因子，权重合计 1.00。因子的选择沿用 stubborn-love 的 feed 打分，但去掉了「资料完整度」和「热度惩罚」，理由见下。

#因子权重算法
① 反向匹配度
我满足对方偏好的比例		 0.40 对方声明的软偏好维度里，我满足几项 ÷ 对方声明的维度数。对方没填偏好 → 1.0
② 正向匹配度
对方满足我偏好的比例		 0.25 同上，方向相反
③ 地域接近 0.15 min(1.0, 同城 1.0 / 同省 0.5 / 否则 0 + 同家乡 0.2)，省份用 city_code / 10000
④ 生活方式相容 0.10 作息、吸烟、饮酒三项中相同的比例。任一方未填的不计入分母
⑤ 活跃度 0.10 exp(-Δ天 / 7)，Δ 取 now() - coalesce(last_active_at, created_at)。7 天时间常数

score = Σ 权重 × 因子，值域 0–1。初始阈值 0.55，双向都要过。

为什么去掉完整度和热度惩罚

  • 完整度。stubborn-love 把它算进 feed 分（权重 0.25）是为了激励补全，在划卡场景有效。但在引荐场景，它会让「资料填得全的人被反复推给所有人」，而不是「最合适的人被推给你」。决策 16 已定完整度只做门槛不做分数，这里必须落实
  • 热度惩罚。它惩罚「最近被很多人右划的人」，为的是防止头部集中。Tidings 没有右划，也没有人气概念 —— 1.3 明确「不做颜值竞技场」。引入热度惩罚等于把攀比逻辑偷偷带回来

权重里 ① 反向匹配度独占 0.40 是这套引擎最重要的取舍：它问的不是「这个人好不好」，而是「这个人会不会回应我」。在主动引荐产品里，后者的价值远高于前者 —— 推一个我看得上但看不上我的人，浪费的是一次推送机会和一次期待。

12.3候选集 SQL

召回部分用一条 SQL，与 stubborn-love 的 feed 一致，用 db.Raw + ? 占位符。

SELECT p.user_id, p.gender, p.birth_ym, p.city_code, p.hometown_code,
       p.height_cm, p.education_level, p.school_tier, p.income_band,
       p.chronotype, p.smoking, p.drinking,
       u.last_active_at, u.created_at
FROM profiles p
JOIN users u ON u.id = p.user_id
LEFT JOIN preferences pref ON pref.user_id = p.user_id
WHERE u.status = 'active'
  AND p.user_id <> ?                                    -- 不是我
  AND p.gender <> ?                                     -- 异性，写死不做同性
  AND p.completeness >= 60                              -- 对方也得过引荐门槛
  -- 硬条件：年龄区间（对方接受我的年龄）
  AND (? IS NULL OR p.birth_ym BETWEEN coalesce(pref.birth_ym_min, 0) AND coalesce(pref.birth_ym_max, 999999))
  AND (? IS NULL OR ? BETWEEN coalesce(pref.birth_ym_min, 0) AND coalesce(pref.birth_ym_max, 999999))
  -- 硬条件：对方接受的城市
  AND (pref.city_codes IS NULL OR p.city_code = ANY(pref.city_codes))
  -- 排重：没有未终结的引荐、没拉黑
  AND NOT EXISTS (
      SELECT 1 FROM introductions i
      WHERE ((i.user_low = ? AND i.user_high = p.user_id)
          OR (i.user_high = ? AND i.user_low = p.user_id))
        AND i.state IN ('pending','viewed','responded')
  )
  AND NOT EXISTS (
      SELECT 1 FROM blocks b
      WHERE (b.blocker_id = ? AND b.blocked_id = p.user_id)
         OR (b.blocker_id = p.user_id AND b.blocked_id = ?)
  )
  -- 不做同性，所以排除自己性别；同城或同省
  AND (p.city_code = ? OR (p.city_code / 10000) = (? / 10000))
ORDER BY random()
LIMIT 200;

13.2时限与到期推进

时限照完整版 PRD 3.1。关键是每个状态的到期时间不同，而状态只前进不后退，所以 expires_at 在每次状态跃迁时重算。

状态进入条件expires_at到期动作
pending生成并已投递created_at + 72h→ expired，发收尾通知
viewed任一方首次打开首次查看 + 7d→ expired
responded任一方表态首次表态 + 7d→ expired
matched双方都 like—建 match + 会话 + 双向推送通知
declined任一方 pass—立即通知等待方（若已有 like）
expired超时存档 90 天可用于模型训练，不重新递出同一条

等待期的计时冻结

决策 03：用户暂停接收引荐期间仍可被别人看到。所以一条引荐可能生成时对方正在暂停。这时：

  • 引荐照常生成并递出给未暂停的一方
  • 暂停方的 expires_at 计时冻结（不推进），因为要求一个不在线的人按时回应是不合理的
  • 暂停方恢复后，按剩余时长重新起算（expires_at = now() + 剩余时长）
  • 另一方全程不知道对方处于暂停状态，他看到的始终是「等待回应」

实现上不引入额外的暂停表：冻结只是「扫描时不处理 expires_at 已过但对手方在暂停的行」，恢复时用 paused_at 重算。这一段逻辑要写单元测试。

13.3单向升级为成对

这是唯一一处需要理解为什么必须有那个部分唯一索引的地方。

场景：A 收到一条 B 的单向引荐（B 不知道），A 点了「想认识」。几天后系统给 B 匹配时又算到了 A，且 B→A 也过线。此时不能插入新行 —— uniq_intro_open_pair 会拒绝，因为 (A,B) 已有一条未终结的引荐。

正确做法是 UPDATE 已有行：把 kind 改成 paired、hidden_side 置空、把 B 侧的 expires_at 重算为「从现在起 72 小时」。B 于是正常收到这条引荐，他看到的是一条全新的引荐，A 此前的等待被保留。

// upgradeToOneway 把一条单向引荐升级为成对。由生成任务在发现
// 「已存在同对的 open 单向引荐」时调用，而不是插入新行。
func (s *Service) upgradeToPaired(ctx context.Context, introID int64, now time.Time) error {
    return s.Repo.Tx(func(tx *gorm.DB) error {
        res := tx.Model(&model.Introduction{}).
            Where("id = ? AND kind = ? AND state IN ?",
                introID, model.IntroOneway,
                []string{model.IntroPending, model.IntroViewed, model.IntroResponded}).
            Updates(map[string]any{
                "kind":        model.IntroPaired,
                "hidden_side": nil,
                "expires_at":  now.Add(72 * time.Hour),
            })
        if res.Error != nil { return res.Error }
        if res.RowsAffected == 0 {
            // 并发中另一方已经升级过了，本次不重复发通知
            return nil
        }
        return s.enqueueIntroDelivered(tx, introID, "paired")
    })
}

RowsAffected == 0 是并发信号，不是错误 —— 与 stubborn-love 处理 matches 唯一冲突的手法一致。

13.4表态的原子性

表态要在一个事务里完成：写动作列 → 判双方是否都 like → 若成立则建 match + 开会话 + 入队匹配通知。任何一步失败全回滚。

func (s *Service) Respond(ctx context.Context, uid, introID int64, action, reason string) (*RespondResult, error) {
    var out *RespondResult
    err := s.Repo.Tx(func(tx *gorm.DB) error {
        // 行锁：双方同时表态时串行化，避免都读到 "对方还没表态"
        var in model.Introduction
        if err := tx.Clauses(clause.Locking{Strength: "UPDATE"}).
            Where("id = ?", introID).First(&in).Error; err != nil {
            return err
        }
        // …所有权校验、状态校验、写动作列、重算 state …

        if in.LowAction != nil && in.HighAction != nil {
            if *in.LowAction == model.ActionLike && *in.HighAction == model.ActionLike {
                return s.createMatch(tx, &in)   // 建 match + 会话 + 入队通知
            }
            return s.closeDeclined(tx, &in)   // 立即通知等待方
        }
        return nil
    })
    return out, err
}

SELECT ... FOR UPDATE 在这里是必需的：双方几乎同时表态时，没有行锁就会各自读到「对方还没动」，两边都不建 match，一对本该成立的人凭空消失。

matches 表的 UNIQUE (user_low, user_high) 是第二道保险。即使行锁失效，唯一冲突也会让重复的那次失败。

14.1密钥与订阅

14.2投递

投递是 outbox worker 的一种 channel。流程与 stubborn-love 的邮件 worker 完全同构：

  1. 按 next_retry_at <= now() AND status = 'pending' 取一批（LIMIT 50），FOR UPDATE SKIP LOCKED
  2. 同事务内把 next_retry_at 推到 now() + 2 分钟作为租约，防止投递期间被重复领取
  3. 事务外真正发起推送
  4. 成功 → status='sent'、写 sent_at、payload 清空为 '{}'（推送内容不该长期留在库里）
  5. 失败 → attempts++，按 [1m, 5m, 30m] 退避；超过 3 次置 failed

投递前必须检查的三件事

// 投递前过滤。这三条对应完整版 PRD 2.5 的防打扰三道闸，
// 但它们不拦「收尾通知」—— 收尾通知不是新招揽（决策 17）。
func (w *OutboxWorker) shouldDeliver(s *model.UserSettings, tpl string, now time.Time) bool {
    isClosing := tpl == model.TplIntroMissed || tpl == model.TplIntroClosed

    // ① 未响应冻结：只拦新引荐，不拦收尾
    if !isClosing && s.PushFrozen {
        return false   // 转站内提示，不推送
    }
    // ② 静默时段：一律推迟到时段结束，不丢弃
    if inQuietHours(s, now) {
        return false   // 重新入队，next_retry_at = 静默结束时刻
    }
    // ③ 暂停接收引荐：只拦新引荐
    if !isClosing && s.IntrosPaused {
        return false
    }
    return true
}
已知代价

收尾通知走推送，会穿透几道防打扰闸门

决策 17 明确收尾通知不受未响应冻结限制，理由是它恰恰要发给不常来的人。但这意味着一个连续两周不打开推送的用户，仍会收到「你错过了 1 位合适的人」。

这是有意的，但有边界：每条引荐只发一次，不做累计，不写「你已错过 N 位」。并且静默时段仍然拦它（推迟到次日，不丢弃）。如果上线后发现收尾通知的卸载投诉上升，第一个要调的就是这个豁免。

14.3失效订阅清理

  • 推送服务返回 404 或 410 → 该 endpoint 已永久失效，直接 disabled_at = now()，不再重试
  • 其他 4xx/5xx → 计入 fail_count，连续 5 次失败后 disabled_at
  • 清理是「软禁用」而非删除：留着行可以统计「多少用户的通知实际上是坏的」，这对判断触达率很有用
运维要点

VAPID 私钥一旦更换，所有既有订阅全部失效

订阅是用公钥生成的，换密钥对等于让所有浏览器上已注册的订阅作废，用户必须重新授权。所以：部署时生成一次，之后只备份不轮换。轮换密钥要有一次性的全量重订阅方案（站内提示 + 引导重新授权），不要临时起意。

三个常驻循环，全在 cmd/worker 里，不引入 cron 库、不加消息队列。

循环周期做什么
outbox2 秒取 pending 通知投递（沿用 stubborn-love 的周期与批大小）
generate5 分钟为活跃用户生成新引荐
expire1 分钟扫描到期引荐，推进状态并发收尾通知

15.1互斥：条件 UPDATE 抢租约

两个 worker 实例同时跑生成任务会重复推人。stubborn-love 全仓库没有任何分布式锁，MVP 也不为此引一个。用一条条件 UPDATE 抢租约，语义与 FOR UPDATE SKIP LOCKED 同源，只是持有时长更长：

-- 抢租约。条件里的 leased_until < now() 保证只有一个实例能成功。
-- 返回行数 = 1 表示抢到，0 表示别人正在跑，本轮跳过。
UPDATE job_runs
SET leased_until = now() + interval '4 minutes',
    last_run_at  = now()
WHERE name = 'intro_generate'
  AND leased_until < now()
RETURNING name;

租约 4 分钟、循环 5 分钟。租约必须短于循环周期，否则上一轮的租约还没过，下一轮永远抢不到，任务静默停摆。这个关系要写成常量并在启动时断言。

注意租约只防重复劳动，不保证正确性。真正的正确性来自 uniq_intro_open_pair：即使两个实例同时跑完全程，唯一索引也会挡住第二行。

15.2生成任务的执行顺序

func (w *GenerateWorker) runOnce(ctx context.Context) error {
    // ① 抢租约，抢不到直接返回
    if ok, err := w.claim(ctx, "intro_generate"); err != nil || !ok {
        return err
    }
    // ② 查池子规模，决定本轮的策略档位（12.4）
    tier, err := w.poolTier(ctx, w.Cfg.City)
    if err != nil { return err }
    if tier == model.PoolTooSmall {
        return nil   // < 100 人，不生成
    }
    // ③ 取这一轮要处理的用户：active、未暂停、距上次收到引荐最久
    users, err := w.pickUsers(ctx, batchSize)
    if err != nil { return err }
    // ④ 逐个生成。单个用户失败不影响其他人
    for _, u := range users {
        if err := w.generateFor(ctx, u, tier); err != nil {
            w.Log.Error("生成引荐失败", "err", err, "uid", u.ID)
        }
    }
    return nil
}

pickUsers 按「距上次收到引荐最久」排序，保证轮流照顾，不会有人被反复推而有人被遗忘。取 batchSize = 200 人一轮。

15.3超时扫描

一分钟一次，走 idx_intro_expire 部分索引，只扫未终结的行。每一行推进状态、写入 outbox、置 closed_at。批量 200 行一轮，避免长事务。

16.2必须照抄的五个细节

细节为什么
用公网端点单独签一次 预签名 V4 把 Host 算进签名，签完再改写 URL 会让签名失效。所以要维护两个 MinIO 客户端：内部端用于读写，公网端只用于签发
object_key 由服务端生成 格式 u/{uid}/{uuid}{ext}。注册时再用 OwnsKey 校验一次前缀，防止客户端拿到预签名后提交别人的 key
服务端处理管线 顺序是：OwnsKey → 扩展名重查 → Get → Stat 判大小 → LimitReader 读 → image.Decode（能解码才算图片，顺带挡掉改后缀的假图）→ 缩放。任一步失败都删掉已传对象
只缩不放 if b.Dx() > width 才缩放。放大一张小图只会得到更大的糊图
桶策略只给 s3:GetObject 一旦允许 ListBucket，任何人都能把全站用户的照片枚举下来，「不可猜」这个前提就不存在了。改这个策略前必须想清楚

16.3三档派生与引荐卡用哪张

const (
    VariantThumb = "thumb" // 200w  会话列表、审核队列

用 JPEG 而不是 WebP：纯 Go 没有可用的有损 WebP 编码器，chai2010/webp 需要 cgo，会破坏 CGO_ENABLED=0 的构建。这是一个已验证的取舍，不要重新论证。

输入侧收 PNG。上面说的都是输出格式，输入没必要跟着一起卡死：image/png 是标准库，同样不引入 cgo，而截图和从聊天里另存出来的图有相当一部分就是 PNG。因为一个顺手就能转掉的格式把用户挡在建档门外，代价远大于收益。所以 UPLOAD_BAD_TYPE 的文案是「只支持 JPEG 和 PNG 图片」，而落库的每一张派生图都是 JPEG。

直传的孤儿对象。预签名 URL 只发票据不写库（用户可能拿了 URL 却不上传），所以「上传成功但没调登记接口」会在桶里留下一份没人引用的对象。M1 不处理，M2 的 worker 加一条清扫：列出对象、删掉没有 photos / profiles.avatar_key 引用且超过 24 小时的。桶策略里匿名只读不含 ListBucket，不影响服务端凭证列对象。

封面照：用 position = 0，不加 is_main 字段

引荐卡需要一张确定的封面。stubborn-love 没有主图概念（只有 position 排序 + 独立的 avatar_key，两张皮）。Tidings 的取舍：

  • 引荐卡封面 = position = 0 的那张照片，用户拖拽排序时第一张天然成为封面，不需要额外的「设为主图」交互
  • 头像仍然是独立的 avatar_key（用于会话列表等小尺寸场景），但它不参与引荐卡
  • 不新增 is_main 列 —— 它和 position 会互相矛盾，且需要一次迁移和一套同步逻辑

16.4照片排序的 DEFERRABLE 约束

沿用 stubborn-love，因为它记录了一个真实的坑和一次失败的尝试：

ALTER TABLE photos
    ADD CONSTRAINT photos_user_id_position_key
    UNIQUE (user_id, position) DEFERRABLE INITIALLY DEFERRED;
  • 为什么必须 DEFERRABLE：拖拽排序在一个事务里交换两个 position，非延迟的唯一约束是逐行检查的，中间态的重复值必然失败
  • 试过的错法：「先把要挪的那张放到负数区间腾位」—— 会撞上 CHECK (position BETWEEN 0 AND 8)；放宽 CHECK 又等于允许脏数据落库
  • 代价要一起接住：DEFERRABLE 的唯一约束不能被 ON CONFLICT 用于冲突推断，所以新增照片不能写 upsert，只能事务内「先查再增改」

17.2中间件分两级

// authed：只要求登录。建档向导挂在这一级 ——
// 用户还没 active，不能用 RequireActive 拦他。
authed := r.Group("/api/v1", h.RequireAuth())

// active：要求已完成建档。引荐、表态、会话挂这一级。
active := r.Group("/api/v1", h.RequireAuth(), h.RequireActive())

这个分法是载重的：stubborn-love 把建档向导放在 authed 而不是 active，否则用户永远填不完建档 —— 填之前他不是 active，不是 active 就走不了建档接口。

RequireAuth 每次都重读 users 行

stubborn-love 明确不加用户缓存，理由是「5 千 DAU 的量级下这就是一次主键查询，不值得为它加缓存；过早缓存会让封禁生效变得不可预测」。Tidings MVP 沿用这个判断。

17.3密码

参数值说明
算法bcrypt，代价因子 12约 200–300ms。顺带就是撞库的天然刹车：单核每秒只能试 3–5 个密码，比任何计数器都硬
最短长度8 位只限长度，不强制字符类别
最长长度72 字节bcrypt 的硬上限，超出部分被静默截断。要在 service 层显式拒绝，不能让它悄悄发生
代价因子范围10–15启动时断言。低于 10 太弱，高于 15 单次登录会超过 1 秒
连续失败锁定5 次 → 锁 30 分钟按邮箱与 IP 两个维度分别计

按 IP 也计一份，是因为只按邮箱计的话，攻击者遍历一份邮箱列表逐个试错，就能把全站账号锁死 —— 那是把防护变成了拒绝服务。

登录流程里的三条纪律

  • 邮箱不存在时也要跑一次 bcrypt 比对（对一个固定假哈希）。否则「立即返回」和「300ms 后返回」的时序差就能枚举出哪些邮箱注册过 —— 这就把 INVALID_CREDENTIALS 那句话白写了
  • 锁定期间不比对密码，直接返回 ACCOUNT_LOCKED（429 + Retry-After）
  • 改密 / 封禁 / 全端登出时递增 token_version，所有已签发的 access token 立即失效

忘记密码

MVP 不做自助找回（需要邮件通道）。M1 提供一个 ADMIN_TOKEN 鉴权的重置接口，运营在后台核对身份后手动重置，并写一条 admin_actions。这条路径的代价是人工，好处是它同时是一次人肉反欺诈核对。

  2. 不用投影分层，用 1px 发丝线和色差。纸是平的。shadow-sm / shadow-md 一律删除。唯一例外是真正浮在纸面上的东西：弹层、抽屉、下拉菜单 —— 它们确实浮着，给一层很轻的阴影是诚实的。
  3. 红色只给印章。错过、超时、失败、审核不通过，一律用 --muted 灰，绝不用红色。这一条有两个理由：1.3 明确不做焦虑营销；而且红色一旦同时表示「你错过了」和「想认识」，印章就失去了它的分量。
状态色

引荐的四种状态，只用灰与青两色

等待中用 --muted，已查看 / 已成匹配用 --accent，已过期 / 已被婉拒用 --muted 且不加重任何视觉 —— 不加红、不加感叹号、不加「已失效」标记。

「已被婉拒」和「已过期」在界面上长得一样，是刻意的：措辞本来就相同（完整版 PRD 3.2），视觉上也不该让他看出区别。

19.2关键界面

四个界面决定了这个产品看起来像不像「有信」。其余页面按同一套规则做即可。

引荐卡 —— 页面的门面

首页空状态 —— 见得最多的一个界面

最容易做错的地方

决策 14 不设保底，意味着「没有引荐」是常态，不是异常

用户可能连续几周打开都是空的。一个写得像故障的空状态，会让用户以为产品坏了并卸载。所以它不能是「暂无数据」，也不能配灰色插画和「去逛逛」。

它应该像一封还没到的信：平静、有交代，并且顺手把该做的事说了。

        ┌─────────────────────────┐
        │                         │
        │           ✉             │  信封线稿，1px 描边，muted
        │                         │
        │    暂时没有新的引荐。     │  思源宋体 17px / ink-2
        │    我们在替你看着。       │
        │                         │
        │   ─────────────────     │
        │                         │
        │   [ 去补全 ]             │  accent 描边按钮，有缺项时才出现
        └─────────────────────────┘

这一屏仍然服务决策 16：只入池的用户能收引荐、不会被引荐。但「你为什么还没被引荐」不再用完成度来说了：百分比和缺项清单都不出现，只给一句平稳的交代，有缺项的人多一个「去补全」的出口。一个可能在池子长大之前连着几周都是空的界面，不适合夹一张催收单（v1.6 改，见 19.2 的「进度」一条）。

收尾通知 —— 已经封上的信

  • 视觉上是一封封着口的信，与引荐卡「拆开的信」形成对照
  • 没有对方照片、没有头像、没有回看入口。引荐已经终结，给回看入口等于给他一个反复点开的机会
  • 全部用 --muted。不用红色、不用感叹号、不用「已失效」标记
  • 「你错过了 1 位合适的人」这句本身压力已经够，视觉不需要再加码

建单向导

  • 表单控件沿用文档的克制风格：1px 线框输入框、4px 圆角、focus 时边框转 accent（不用外发光环）
  • 连续数值（身高、体重、收入区间）用滚轮选择器，不用滑块。滑块在手机上很难精确停在 165。身高与体重是一组，控件也同形：都是带单位的选项表（165 cm / 52 kg），都用原生下拉——手机上它就是系统滚轮，而且不像自绘滚轮那样需要「初值落在中位数」，因为原生下拉不强迫人从最小值滚起
  • 出生日期、所在城市、家乡各是一个字段，点开是底部弹层，里面是滚轮。出生日期一屏三列（年 | 月 | 日），城市和家乡一屏两列（省 | 市，滚省时右边的市整列跟着换）。不做「三个并排的下拉」——同一个问题摊成三个控件，用户得依次点开三次系统滚轮，而两列并排还能让「先省后市」这个层级关系一眼看得见。点「完成」才落库，滚轮只改弹层里的草稿（见 5.3「省市两级弹层」）
  • 自绘滚轮比原生控件对键盘和读屏更不友好，这是它的代价：列容器挂 role="listbox"、选项挂 role="option" 并支持方向键 / PageUp / PageDown / Home / End，弹层本身有焦点陷阱、Escape 关闭与背景滚动锁。弹层不做入场动画——全站唯一的动效是印章（19.3）
  • 进度不报百分比、也不列缺项清单：入池与否只有两种状态，向导一步步往下走本身就是进度，顶上再挂一张此刻够不着的清单只会添负担。满足时说一句「入池条件已满足，可以收到引荐了」，缺项只在编辑页里对着字段看。不写「完善资料」，也不写「档案 45%」——后者会让人以为没到 100% 就不能被引荐（v1.6 改）
  • 每一步提交即保存（PUT /me/profile 局部更新），顶部不设「保存」按钮

19.3印章：全站唯一的动效

「想认识」这个动作，做成盖章。

信纸、写信、表态 —— 这套隐喻里，「想认识」最自然的对应不是按钮变蓝，是落一枚印。而且它有一个真实的好处：「想认识」是不可撤销的，盖章这个动作本身就传达出了不可撤销。

  • 点击后，一枚方形印章（--seal 红，2px 圆角，内含思源宋体「信」字）从 1.6 倍缩到 1.0，同时旋转 −8°，透明度 0 → 1，220ms cubic-bezier(.2,.8,.2,1)
  • 落定后用 mix-blend-mode: multiply 加 0.4px 模糊，模拟墨渗进纸纤维
  • 停留 500ms，让用户看清自己盖了什么，然后卡片上滑淡出
  • API 请求在点击瞬间发出，不等动画。动画只是覆盖掉网络延迟，不能变成延迟
  • prefers-reduced-motion: reduce 时直接切状态，无缩放无旋转
尺度

全站只有这一处动效，其余一律不做

页面切换不做过渡、列表不做入场动画、卡片不做悬停位移、滚动不做视差。让印章成为唯一一个「会动的东西」，它才有分量。到处都是动效的产品，没有一个动作会被记住。

唯一的例外是加载态（骨架屏、按钮内的 spinner）—— 那是反馈，不是装饰。

19.4响应式

移动优先，桌面完整可用。不沿用 stubborn-love 的 480px 死宽 —— 那个宽度在电脑上是一条居中的窄缝，如果种子用户从电脑点开链接，第一印象会很差。

断点布局
< 640px单列满宽，引荐卡占满，底部安全区留白。底部导航固定
≥ 640px内容居中 max-w-[880px]，引荐列表双列。阅读类页面（引荐详情、会话）收窄到 max-w-[640px]，保持接近 65 字符的行宽
≥ 1024px左侧固定导航栏替代底部 tab，内容区不变
  • 触控目标高度 ≥ 44px（iOS HIG 的最小值）。「不合适」虽然是静默按钮，点击区仍要够大
  • 配 viewport-fit=cover 与 env(safe-area-inset-*)，底部 tab 栏避开 iPhone 的横条
  • 桌面端不放大字号、不拉伸卡片 —— 只增加列数和留白

19.5iPhone 安装引导

触达的前提

iOS 上不装到主屏幕，就收不到任何推送

Safari 从 iOS 16.4 起支持 Web Push，但只对「已添加到主屏幕」的 Web App 生效：普通 Safari 标签页里的网页拿不到推送权限，PushManager 根本不存在。macOS 上的 Safari 同样要求把站点添加到程序坞。

对一个推送即产品的应用，这意味着安装引导不是增长手段，是触达的必需环节。安卓 Chrome 与桌面 Chrome / Edge / Firefox 不需要安装即可推送，所以这套引导只对 iOS / macOS Safari 显示。

  • 检测：/iPad|iPhone|iPod/.test(navigator.userAgent) 且 !window.matchMedia('(display-mode: standalone)').matches 且 !navigator.standalone。已安装的用户靠 display-mode 判断，不依赖任何存储标记
  • 展示时机：建档完成之后、请求推送授权之前 —— 与完整版 PRD 8.1 的授权时机同一个位置，一次讲完「为什么需要装」和「装完能得到什么」
  • 内容：Safari 底部分享按钮的位置说明 + 「添加到主屏幕」+ 从主屏打开。分享图标用内联 SVG 画，不用 emoji（emoji 在不同系统上长得完全不一样，指不清位置）
  • 不做的事：不弹遮罩阻断操作、不反复出现、不诱导。用户跳过就跳过，用站内未读角标兜底
  • 推送授权必须在用户手势里请求，不能在页面加载时自动调 subscribe() —— iOS 会直接拒绝且不再给第二次机会
  • 这套判断涉及系统 UI 的具体位置，上线前必须在真机上逐版本验证（iOS 16.4 / 17 / 18 的分享菜单位置改过）

邮箱不验证，批量注册比手机号便宜得多 完整版 PRD 10.1 的四条必须项里，手机号那条删除（它是身份门槛），其余三条照旧。但这三条不是同时生效的：真实人像检测 M1 就有（头像必过 pigo 正脸检测），照片先审后发与入池前文本先审要等 M5 的审核队列 —— M1–M4 期间照片与文本是即时生效的，头像字段虽已带 avatar_review_state='pending'，但它不挡任何东西。也就是说上线初期唯一真正在跑的自动门槛是人脸检测，别把它当成三条都在。注册侧另有单 IP 每日 10 个的限流，以及 15 个最常见一次性邮箱域名的黑名单（EMAIL_REJECTED）—— 后者便宜且不误伤，但只是抬高一点成本，不是解决方案 种子期手动抽查注册来源 IP 分布。如果假档案开始稀释引荐质量，就说明那三条必须项没兜住，这时才需要考虑补验证，而不是先补
直传的孤儿对象：上传成功但没登记 预签名 URL 只发票据不写库，用户拿到 URL 后可以传完就走，桶里于是留下没有 photos / profiles.avatar_key 引用的对象。M1 不处理（UPLOAD_TOO_LARGE 与 UPLOAD_BAD_TYPE 拦下的那批同样留在桶里） M2 的 worker 加一条清扫：列出对象，删掉无引用且超过 24 小时的。存储成本之外还有一层 —— 桶会变成一个没有访问控制的公共读空间，任何写进去的东西都能通过 /img/ 取出来，所以这条不能一直挂着
注册接口天然泄露「某邮箱是否已注册」 不告诉用户邮箱被占了，他就不知道该怎么办；改成不泄露会让注册无法完成。登录接口不泄露 接受。靠 IP 限流压住枚举速度，并把这条写进接口文档的已知行为
没有自助找回密码，忘记密码只能找运营 M1 就上 POST /api/v1/admin/users/:id/password，README 附 curl；注册页明写「忘记密码请联系客服」 看客服工单量。这个数字同时是「用户有多在意这个账号」的代理指标，量大的话 V1.1 的邮件通道优先级要往上提
通知偏好、账号变更都只能站内说 没有邮件通道，所有「系统要告诉用户的事」都只能靠推送或站内提示 推送权限被拒的用户等于半失联。检测方式：push_subscriptions 有效订阅数 / status='active' 用户数
iPhone 用户不装到主屏就收不到推送，而 MVP 没有邮件兜底 安装引导放在建档完成之后、授权之前（19.5）；靠站内未读角标兜底 种子期就要盯 push_send_total 的覆盖人数 —— 如果 iPhone 用户的订阅数明显低于安卓，说明引导没生效，这时再补邮件通道就已经晚了
最需要盯的一条

推荐机制坏掉时不会报错

接口 200、任务照跑、日志干净，但没有任何人被推 —— 因为某个条件写错了，候选集永远是空集。这类故障在别的系统里会被错误率兜住，在这里不会。

所以 MVP 必须有一条主动的健康指标：池子规模、每轮生成出的引荐数、候选集召回数。任一为 0 且持续，就要告警。不要等到用户投诉才发现没人在被推荐。
